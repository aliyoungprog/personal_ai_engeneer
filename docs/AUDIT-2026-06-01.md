### [autonomy] Transient-failure auto-requeue forms an unbounded infinite retry loop
- **Where:** `/Users/abdu/Documents/personal/personal_ai_engeneer/src/ai_agent/services/task_execution_service.py:220-234`
- **Issue:** On any failure classified as transient (_is_transient_failure matches generic substrings like 'failed to connect', 'unable to access', 'operation timed out'), _handle_failure calls reset_for_retry(), which sets decision=PENDING and clears notified_at. On the next poll, process_poll_result re-sends the task card (intake_service.py:45) and re-marks notified. There is no attempt counter, no max-retry cap, and no backoff. If the underlying condition persists (VPN stays down, git host unreachable, OAuth permanently revoked and surfacing a connect-like error) the task is offered → accepted (auto or by the user) → fails transiently → requeued, forever. Worse, the substring matcher is broad: a coder/reviewer AgentError whose details merely contain a phrase like 'unable to access' would be misclassified as transient and looped instead of staying failed. Unattended, this produces an endless churn of runs, worktrees, MRs-attempts and Telegram notifications.
- **Fix:** Add a per-task retry counter (e.g. transient_retries column) and cap it (e.g. 3) with exponential backoff via defer_until before re-offering; only requeue when count < cap, otherwise mark failed with a manual-retry button. Tighten _is_transient_failure to inspect a structured error type/category rather than free-text substrings of error.details.

### [autonomy] inactivity_timeout_seconds is declared but never enforced — a silently stalled Claude CLI blocks for the full 1800s
- **Where:** `/Users/abdu/Documents/personal/personal_ai_engeneer/src/ai_agent/ai/claude_runner.py:67-69`
- **Issue:** ClaudeRunRequest.inactivity_timeout_seconds (default 300) is documented as 'If no stream event arrives for this long, assume the CLI is stalled (silently waiting on a rate-limit window) and bail out.' but grep shows it is referenced nowhere except its declaration. Neither _run_blocking nor _run_streaming implements an inactivity watchdog; the only enforced limit is the hard timeout_seconds (1800 in _execute). The streaming watchdog (claude_runner.py:237) fires only at the hard timeout. Consequence for an unattended agent: when the Claude OAuth token expires mid-run or the CLI silently waits on a rate-limit reset, the subprocess produces no events but is not killed for up to 30 minutes, and because of the global asyncio.Lock (start/_run_safe) the entire pipeline is frozen for that whole window for every queued task.
- **Fix:** Implement the documented inactivity watchdog: in _run_streaming track monotonic() of the last event and have a periodic timer kill proc if now - last_event > inactivity_timeout_seconds; for _run_blocking, fall back to a shorter effective timeout or run via the streaming path so stalls are detected. Surface inactivity kills as a distinct (non-transient) error.

### [autonomy] No Claude OAuth token-expiry handling: mid-run expiry surfaces as a generic failure with no refresh or distinct signal
- **Where:** `/Users/abdu/Documents/personal/personal_ai_engeneer/src/ai_agent/ai/claude_runner.py:284-352`
- **Issue:** The runner only distinguishes timeout, blocking rate-limit, and non-zero exit. There is no detection of an auth/OAuth-expiry condition (the container cannot auto-refresh the Claude token per MEMORY: it must be synced from the macOS Keychain). When the token expires mid multi-hour run, the CLI either prompts (and stalls → see inactivity finding) or exits non-zero with an auth error; this maps to a generic 'exit code N' AgentError. _is_transient_failure will NOT match auth errors, so the run is marked failed permanently with no operator-actionable signal and no requeue — the agent silently stops doing work until a human notices and re-syncs the token. Consider a lightweight token-validity preflight in _run_safe before acquiring expensive resources.

### [autonomy] Global asyncio.Lock serialises ALL runs, so one stuck run blocks the entire queue with no abort
- **Where:** `/Users/abdu/Documents/personal/personal_ai_engeneer/src/ai_agent/services/task_execution_service.py:181,200,205-218`
- **Issue:** start() fire-and-forget creates a task that immediately does `async with self._lock` in _run_safe. The lock is a single instance-level asyncio.Lock, so only one task can execute at a time across the whole process. Combined with the 1800s hard timeout and the missing inactivity watchdog, a single run that stalls (token expiry, rate-limit wait, hung subprocess) holds the lock for up to 30 minutes, during which every other accepted task queues behind it with zero visibility. There is also no abort: cancel() (line 545) does NOT hold or interrupt anything running under the lock and cannot stop the in-flight asyncio task or kill the Claude subprocess (P2). An unattended operator has no way to free a wedged queue short of restarting the process.
- **Fix:** Either (a) bound the lock scope to only the truly serial sections (repo clone / shared git index) and allow per-worktree runs to proceed concurrently, or (b) keep serial execution but add a hard run-level deadline far below the lock-starvation point and an abort path that cancels the tracked asyncio.Task and kills the subprocess. At minimum, track and expose queue depth and the holding run id.

### [claude_runner] Watchdog kill leaves orphaned grandchild processes (Bash/pytest/node descendants)
- **Where:** `src/ai_agent/ai/claude_runner.py:235`
- **Issue:** On hard timeout the watchdog calls proc.kill(), which sends SIGKILL only to the direct child (the `claude` node process). The subprocess is launched WITHOUT start_new_session/process_group, so any descendants the claude CLI has spawned (Bash tool invocations, pytest, uv, python, mypy, an MCP server, or node sub-processes) are NOT in a killable group and survive. For an UNATTENDED agent running many tasks, every timed-out run can leak long-lived grandchildren (e.g. a hung pytest or a `python` process), accumulating until the host/container is starved of CPU/RAM/file handles. Worse: a leaked grandchild may still hold the stdout pipe open, so even though proc.kill() killed `claude`, the readline() loop below (line 248) can keep blocking on the inherited write-end of the pipe and never see EOF — the watchdog 'fired' but the worker thread stays stuck forever. The same orphan problem exists for the buffered path's TimeoutExpired (subprocess.run also only kills the direct child).
- **Fix:** Launch with start_new_session=True (POSIX) so the child becomes a process-group leader, and on timeout send the signal to the whole group: os.killpg(os.getpgid(proc.pid), signal.SIGKILL) (guard with try/except ProcessLookupError). Do a SIGTERM-then-SIGKILL escalation. This also guarantees the pipe write-ends are closed so readline() gets EOF. Apply the same group-kill in _run_blocking by replacing subprocess.run with a Popen you can killpg on TimeoutExpired.

### [claude_runner] inactivity_timeout_seconds is declared but never enforced — the documented stall protection does not exist
- **Where:** `src/ai_agent/ai/claude_runner.py:69`
- **Issue:** ClaudeRunRequest.inactivity_timeout_seconds (default 300s) is documented as 'If no stream event arrives for this long, assume the CLI is stalled (silently waiting on a rate-limit window) and bail out.' But grep across the codebase shows the field is only ever defined — it is never read in claude_runner.py or any caller. The streaming loop's proc.stdout.readline() (line 248) is an unbounded blocking call; the ONLY timeout is the hard watchdog at timeout_seconds (default 1800s = 30 min). So the exact failure mode this field was meant to catch — the CLI going silent while sitting in a rate-limit backoff or a stuck MCP/init — is NOT caught early. An unattended run that stalls at minute 1 will hold the worker thread and block the run for the full 30 minutes before the hard watchdog fires, instead of bailing in 5 minutes. rate_limit_wait_threshold_seconds (line 72) is likewise dead — the documented 'bail immediately if the reset window is far away' logic is never implemented; _finalize only inspects rate-limit state AFTER the process has already exited or timed out.
- **Fix:** Implement an inactivity watchdog: track a 'last event' monotonic timestamp updated on each readline, and have a timer (or a second watchdog that reschedules itself) kill the process group if now-last_event exceeds inactivity_timeout_seconds. Alternatively run readline in a way that supports a per-read deadline (e.g. select on the fd). For rate_limit_wait_threshold_seconds, when a blocking rate_limit_event with a far-future resetsAt arrives, proactively terminate instead of waiting. If these are intentionally unused, delete the fields and the misleading docstrings so callers don't rely on protection that isn't there.

### [concurrency] Shared asyncio.Lock on a singleton service serializes every task run for its entire lifetime
- **Where:** `/Users/abdu/Documents/personal/personal_ai_engeneer/src/ai_agent/services/task_execution_service.py:200`
- **Issue:** TaskExecutionService is registered as a providers.Singleton (di_container.py:86), so self._lock (created once at __init__, line 181) is a single process-wide lock. _run_safe acquires it with `async with self._lock` and holds it for the WHOLE pipeline: PREPARING -> (CODING -> TESTING -> REVIEWING -> TESTER) * max_iterations -> PUSHING -> AWAITING_APPROVAL, with coder/reviewer/tester each running a 1800s-timeout Claude subprocess. Because start() (line 194) fires the run as a detached create_task and returns immediately, the user can accept a second task while the first is mid-run. The second run's coroutine then blocks on the lock acquisition silently and indefinitely (up to the full duration of run #1, potentially tens of minutes), with no Telegram feedback and no TaskRun row created (create_for_task is INSIDE the lock at line 201). For an unattended agent this looks like the second accepted task simply vanished. Worse, _run_safe only releases the lock on completion/exception; AWAITING_APPROVAL is reached while still holding the lock? No — _execute returns at AWAITING_APPROVAL so the lock IS released there, but every active coding run still fully blocks any other run start.
- **Fix:** Decide the intended concurrency model. If runs are meant to be serial, that is fine but you MUST give immediate feedback: do create_for_task and a 'queued, waiting for the current run' Telegram notice BEFORE awaiting the lock, or use an explicit bounded asyncio.Queue/worker so queued runs are visible. If runs are meant to be concurrent, replace the single shared lock with a per-worktree/per-task guard (e.g. a dict of locks keyed by slug) so distinct tasks do not serialize. Either way, do not perform DB row creation inside the contended lock.

### [executor] FAILED run leaks its worktree and branch (never cleaned up)
- **Where:** `src/ai_agent/services/task_execution_service.py:213-218`
- **Issue:** When _execute raises (coder failure, gates failed after max_iterations, reviewer requested changes, QA failed, or any crash), _run_safe calls mark_failed + _handle_failure but NEVER calls _cleanup_worktree. The on-disk worktree directory (self._root/slug) and the local branch ai-agent/<slug> are left behind. _cleanup_worktree is only invoked from approve_and_merge (success) and cancel (manual). Over an unattended agent's lifetime every failed task accumulates a worktree dir + dangling branch, consuming disk and polluting the local clone. The create() path does try to remove a stale same-slug worktree on the NEXT run for the same task, but distinct failed tasks never get reclaimed, so the leak grows unbounded.
- **Fix:** In _run_safe's except blocks (and/or in _handle_failure), call await self._cleanup_worktree(run) in a try/except before/after marking failed. Since set_worktree is called early in _execute, run.branch_name will be populated for any failure after PREPARING; guard for the case where it failed before worktree creation (branch_name is None — _cleanup_worktree already no-ops on that).

### [executor] asyncio.Lock held for the entire multi-minute run blocks approve/cancel and serializes everything
- **Where:** `src/ai_agent/services/task_execution_service.py:181,200`
- **Issue:** _run_safe wraps the whole _execute (clone, up to max_iterations=7 coder passes at 1800s timeout each, gates, reviewer, tester, push, MR creation) in `async with self._lock`. The same TaskExecutionService instance is a singleton (get_container().task_execution_service()), and start() fire-and-forgets _run_safe. Consequences for an unattended agent: (1) If a user accepts a second task while one is running, its _run_safe blocks on the lock for potentially tens of minutes with zero feedback — it looks hung. (2) More subtly, the lock does NOT protect approve_and_merge/cancel (they don't acquire it), so the lock is not actually providing a coherent mutual-exclusion contract — it only serializes new runs, while still allowing concurrent merge/cancel that mutate worktrees. The intent (one run at a time) is achieved only by accident and at the cost of unbounded queuing latency.
- **Fix:** Either (a) don't hold a global lock across the whole run — instead reject/queue a new start() fast when one is active (e.g. lock only around an 'is a run active?' check + set flag, releasing immediately, and bail with a user-visible 'busy' message), or (b) if true serialization is desired, make it explicit and bounded and ensure approve/cancel cannot run concurrently with an active _execute on the same worktree. At minimum notify the user that the task is queued behind the lock.

### [executor] cancel() removes the worktree out from under a still-running execution
- **Where:** `src/ai_agent/services/task_execution_service.py:534-545`
- **Issue:** cancel(run_id) calls _cleanup_worktree (git worktree remove --force --force + branch -D) and sets status=CANCELLED, but it does NOT stop the background _run_safe/_execute task — start() fire-and-forgets the task and keeps no handle to it, so there is nothing to cancel. If the user cancels while the coder/gates/git is mid-run, git worktree remove --force races against an active Claude process writing files / a running git command in that same path. This corrupts the worktree, can crash the live _execute with confusing GitError mid-stage, and the still-running _execute will then continue and overwrite the CANCELLED status (e.g. push to AWAITING_APPROVAL or mark_failed), so the cancel is silently ignored. Also CANCELLED is set via raw run.save while _run_safe may concurrently mark_failed/set_status the same row — last-writer-wins on status.
- **Fix:** Track the background task handle (e.g. dict run_id->asyncio.Task in start()), and in cancel() request cooperative cancellation: cancel the task, await its completion/cancellation, THEN clean up the worktree and set CANCELLED. Have _execute check a cancellation flag at stage boundaries before mutating the worktree.

### [gates] pytest exit code 5 (no tests collected) is treated as a gate failure, blocking the agent unattended
- **Where:** `src/ai_agent/gates/check.py:315`
- **Issue:** _gate_pytest computes passed = not timed_out and exit_code == 0. pytest returns exit code 5 when no tests are collected. _select_test_targets can legitimately produce targets that collect zero tests: a changed file matched as a 'test file' by _is_test_file (name startswith test_ / has 'tests' in path / endswith _test.py) may actually be a fixtures/helpers/conftest-style module with no test functions, or a real test file whose tests were all renamed/removed in this same change, or files under a directory whose 'tests' component is incidental. In all those cases pytest exits 5 and the gate FAILS even though nothing is wrong. For an unattended agent this is a hard block: it will loop trying to 'fix' a failing test gate that has no actual failing test, and the feedback_for_claude message tells it to fix source it never broke. Optionally pass --no-header and parse 'no tests ran' to distinguish from real collection errors.

### [git_ops] Re-run push fails non-fast-forward: branch recreated from base but force_with_lease never set
- **Where:** `src/ai_agent/git_ops/worktree.py:143`
- **Issue:** On any retry/re-run of a task that previously reached PUSHING, create() does `branch -D` and recreates the local branch fresh from origin/<default> (lines 92, 98-106). The prior run's remote branch `origin/ai-agent/<slug>` still exists on the host. The only caller, task_execution_service.py:491, calls `push(handle)` with the default `force_with_lease=False`, so push() runs plain `git push -u origin <branch>` (lines 146-151). Because the recreated branch does not contain the old remote commits as ancestors, the remote rejects it as `non-fast-forward` and the run dies at PUSHING. I reproduced this end-to-end: run-1 push, remove+branch -D, recreate from base, run-2 `push -u` -> `! [rejected] (non-fast-forward)`. This bites the manual-retry path that the project explicitly supports (MEMORY: P1 idempotent re-run), so an unattended retry of a task that got far enough to push will fail forever.
- **Fix:** Pass force_with_lease=True on the push for the agent's own short-lived branches (the agent fully owns ai-agent/<slug>), OR have create() delete the stale remote branch (`git push origin --delete <branch>`, ignore failure) before recreating. Note force-with-lease also relies on `origin/<branch>` being current — ensure_cloned()'s `fetch --prune` runs before create(), so the lease ref is fresh; that path verified working.

### [git_ops] Titles producing '..', a trailing '.', or a '.lock' component yield invalid git refnames; worktree creation crashes at PREPARING
- **Where:** `src/ai_agent/git_ops/worktree.py:49`
- **Issue:** _SLUG_RE permits '.' so titles like 'compare v1..v2' -> 'T-1-compare-v1..v2', 'update README.' -> 'T-1-update-readme.', and 'fix .lock issue' -> 'T-1-fix-.lock-issue' survive slugging unchanged (the `-+` collapse does not touch dots). ### [infra] Fire-and-forget execution task can be garbage-collected mid-run
- **Where:** `/Users/abdu/Documents/personal/personal_ai_engeneer/src/ai_agent/services/task_execution_service.py:194`
- **Issue:** start() does `asyncio.create_task(self._run_safe(task), name=...)` and discards the returned Task. The event loop only keeps a weak reference to running tasks, so per the asyncio docs the task may be garbage-collected before it finishes, silently cancelling a run that is cloning/coding/pushing. This is the documented 'fire-and-forget task GC' footgun. For an unattended agent a run can vanish with no error, no FAILED state, and a leaked worktree. ### [infra] Shutdown closes DB and clients while in-flight runs and cancelled tasks are still executing
- **Where:** `/Users/abdu/Documents/personal/personal_ai_engeneer/src/ai_agent/main.py:93`
- **Issue:** After asyncio.wait(FIRST_COMPLETED), the code calls poller.request_stop(), then `for t in pending: t.cancel()` but never awaits the cancelled tasks, then immediately awaits telegram.close(), notion.close(), database_disconnect(). Two problems: (1) cancellation is asynchronous — the supervise/poll/telegram tasks may still be mid-await when their underlying Telegram session, Notion client, and Tortoise connections are torn out from under them, producing spurious exceptions during shutdown. (2) Any background execution task spawned by TaskExecutionService.start() (a separate create_task) is not in the pending set at all, so a run that is mid-flight at SIGTERM keeps running against a DB whose connections were just closed by database_disconnect(); the next run.save()/mark_failed() raises on a closed pool, leaving the TaskRun stuck in a non-terminal status and a dirty worktree.
- **Fix:** Cancel pending tasks and await them with asyncio.gather(*pending, return_exceptions=True) before closing clients/DB. Also track in-flight execution tasks (see other finding) and await/cancel them during shutdown so the DB is closed only after all DB users have stopped.

### [intake_poller] Accept while a run is already in progress spawns a second run / duplicate MR
- **Where:** `/Users/abdu/Documents/personal/personal_ai_engeneer/src/ai_agent/services/task_decision_service.py:21-26`
- **Issue:** accept() unconditionally sets decision=ACCEPTED and calls execution.start(task) with no guard against an already-running or completed run for the same task. Telegram callback buttons are not idempotent: a double-tap, a Telegram callback retry, or simply pressing Accept again on a card that was never edited away will call accept() twice. execution.start() is fire-and-forget (asyncio.create_task) and creates a brand-new TaskRun each time (TaskRunsRepository.create_for_task always inserts). Also disable/replace the inline keyboard buttons in handlers.on_decision after the first successful action so the card cannot be re-actioned.

### [intake_poller] defer() never sets defer_until and the poller never re-surfaces deferred tasks

### [reviewer_tester] _extract_last_json mis-parses any verdict whose string values or trailing prose contain braces
- **Where:** `src/ai_agent/ai/reviewer.py:197-206`
- **Issue:** _JSON_OBJECT_RE = re.compile(r"\{(?:[^{}]|(?:\{[^{}]*\}))*\}") only tolerates ONE level of nested braces, and re.findall returns the last MATCH (which may be an inner brace group), not the last top-level object. Add unit tests for: nested objects in lists, braces inside string values, and prose-with-braces after the JSON.

### [telegram] Truncation of rendered HTML splits entities/tags causing Telegram 400, aborting MR notification
- **Where:** `/Users/abdu/Documents/personal/personal_ai_engeneer/src/ai_agent/clients/telegram_client.py:48`
- **Issue:** _md_to_tg_html escapes + renders markdown to HTML and only then slices the result at _MR_BODY_LIMIT (text[:3500]). ### [intake_poller] approve_mr / cancel_run have no guard against being invoked twice or on a finished run beyond status-check race
- **Where:** `/Users/abdu/Documents/personal/personal_ai_engeneer/src/ai_agent/services/task_execution_service.py:509-545`
- **Issue:** approve_and_merge re-reads the run and checks status==AWAITING_APPROVAL, which is good, but cancel() has NO status guard at all: it can be called on a DONE/MERGING/FAILED run and will blindly remove the worktree and force status=CANCELLED, overwriting a terminal state. Combined with non-idempotent Telegram buttons, a user (or callback retry) hitting Cancel after a merge has started can clobber a MERGING/DONE run's status to CANCELLED and attempt to delete a worktree that approve_and_merge is concurrently using. There is no lock shared between approve and cancel.
- **Fix:** In cancel(), refuse if run.status is already terminal (DONE/FAILED/CANCELLED) or actively MERGING; only allow cancel from non-terminal pre-merge states. Guard both approve and cancel under the same lock used by _run_safe so a run cannot be merged and cancelled concurrently.
